第 1 章　认识 DSH：模型、Harness、Agent

约 5 分钟 · 2,301 字 · 10 个小节

本章你会学会

  • 用一句话解释 DSH 是什么；
  • 分清“模型”“Harness”“Agent”三个容易混淆的词；
  • 知道 Session、Workspace、Tool、Skill 分别在说什么；
  • 知道自己该用 Desktop、Web 还是 Headless。

1.1 一个公式：Agent = Model + Harness

先记住一个公式：

Agent = Model + Harness

拆开看：

词 你可以把它理解成 它负责什么
Model（模型） 大脑 理解你的话、推理、写文字、写代码
Harness（脚手架/工作台） 手、眼睛、工具箱、工作台、规章制度 读写文件、执行命令、搜索网页、保存会话、控制权限
Agent（智能体） 正在工作的助手 模型 + Harness 组合起来，真正去完成任务

如果只有模型，它像一个很聪明但被关在房间里的人：能思考、能说话，但看不见你的文件，也不能帮你运行程序。

Harness 把房间打开：给它文件、终端、浏览器、工具、记忆和规则。它才能从“聊天”变成“干活”。

DeepSeek Harness，简称 DSH，就是这样一个 Harness。

1.2 DSH 是什么，不是什么

它是

  • 一个运行 Agent 的工作台；
  • 一个可以把模型、工具、技能、插件组合起来的宿主；
  • 一个支持 Desktop、Web、Headless 多种入口的平台；
  • 一个“几乎一切皆插件”的可扩展系统。

它不是

  • 不是模型本身。DSH 不包含“DeepSeek 的大脑”，你要连接一个模型服务。
  • 不是普通的聊天软件。它的重点不是陪你聊天，而是读写文件、执行任务、交付结果。
  • 不是只有程序员才能用。日常任务完全可以用自然语言完成。
  • 不是绝对安全的。它能执行真实操作，所以权限和审查很重要。

一句话：

DSH 是 Agent 的工作台，不是 Agent 的大脑。

1.3 五个核心词

先认识五个词，后面会反复出现。

Agent：正在工作的助手

Agent 不是“一个模型”，而是“模型 + 当前工作区 + 当前会话 + 可用工具 + 当前模式”的组合。

同一个模型，换一个工作区、换一个模式，能力就不一样。

Session：一次对话

Session 是你和 Agent 的一次连续对话。

  • 同一个 Session 里，它记得前面说过什么；
  • 新建 Session，它不会自动继承上一个 Session 的全部上下文；
  • 一个工作区可以有很多 Session。

你可以把 Session 理解成“一次会议记录”。

Workspace：工作区

Workspace 是一个文件夹。Agent 默认在这个文件夹里读文件、写文件、执行命令。

  • 工作区是你的“项目边界”；
  • Agent 的很多权限，都以工作区为边界；
  • 不要一上来就把整个用户目录当工作区。

Tool：工具

Tool 是 Agent 能执行的一个动作，比如：

  • 读文件；
  • 写文件；
  • 修改文件；
  • 执行终端命令；
  • 搜索网页；
  • 启动子代理；
  • 交付文件。

Tool 是 Agent 的“手”。

Skill：技能

Skill 是一份“操作手册”，告诉 Agent：

  • 遇到某类任务时，应该先做什么、后做什么；
  • 有哪些注意事项；
  • 可以调用哪些脚本或参考资料。

Skill 不是工具，它不直接执行动作；它是知识，帮助 Agent 更稳定地使用工具。

Tool 是“手”，Skill 是“操作规程”，Model 是“大脑”，Harness 是“工作台”。

后面还会遇到 Preset、Plugin、Bundle、Profile，先不用急，第 7、8 章会讲。

1.4 为什么需要 Harness

你可能会问：模型已经很聪明了，为什么还要 Harness？

因为真实任务需要三样模型本身没有的东西：

  1. 感知：看见你的文件、目录、网页、报错；
  2. 行动：写文件、跑命令、调用工具；
  3. 约束：知道哪些能做、哪些不能做、做完怎么验收。

举个例子。你说：

“帮我把 notes/ 里的三篇文章合并成一份摘要。”

模型可以写摘要，但它需要 Harness 帮它：

  • 找到 notes/ 目录；
  • 读取三个文件；
  • 写入 summary.md；
  • 确认文件真的写成功了；
  • 在你允许的范围内操作。

没有 Harness，这些动作都发生不了。

1.5 三种入口：Desktop、Web、Headless

DSH 可以用不同方式启动。对 0 基础用户，建议从 Desktop 开始。

入口 适合谁 特点
Desktop 绝大多数人 图形界面，点按钮，最容易上手
Web 想在浏览器里用、或跑在远程服务器上的人 打开一个网址，界面与 Desktop 类似
Headless 自动化、脚本、批量任务 命令行一次性执行，没有图形界面

三种入口共享同一套核心概念：Agent、Session、Workspace、Tool、Skill、Preset、Plugin。

本书以 Desktop 为主。遇到 Web/Headless 的不同之处，会用“换一种入口”小栏说明。

1.6 本书怎么读

  • 日常用户：读第 1–7 章，足够覆盖 90% 的使用场景。
  • 想装插件/技能：加读第 8 章。
  • 想做插件：再加第 9 章。
  • 遇到问题：直接翻第 10 章。

不要试图一次记住所有名词。先会用，再理解。

马上试试

拿出一张纸，写下你想让 Agent 做的三件事。每件事标注：

  1. 它需要读哪些文件？
  2. 它需要写哪些文件？
  3. 它需要运行什么命令？
  4. 哪些操作你希望它先问你？

写不出来也没关系，第 3 章会教你怎么把任务说清楚。

常见坑

  • 把 DSH 当成模型：DSH 只是工作台，模型要单独连接。
  • 把 Agent 当成永远记得一切的人：Session 之外的记忆需要你自己设计。
  • 一上来就给整个硬盘权限：先用一个专门的小文件夹。

小结

  • Agent = Model + Harness。
  • DSH 是 Harness，不是模型。
  • Session 是一次对话，Workspace 是一个文件夹，Tool 是动作，Skill 是知识。
  • Desktop 最适合入门；Web 和 Headless 是不同入口，不是不同产品。

第 2 章　第一次启动：桌面、模型、工作区

约 4 分钟 · 1,913 字 · 11 个小节

本章你会学会

  • 打开 DSH Desktop；
  • 连接一个模型；
  • 选一个安全的工作区；
  • 用标准模式完成第一次只读对话；
  • 看懂界面上的工具卡片和审批提示。

2.1 打开 Desktop

安装完成后，打开 DeepSeek Harness。

第一次打开时，你可能会看到：

  • 欢迎页；
  • 模型/账号设置；
  • 工作区选择；
  • 新建任务输入框。

不同版本界面会略有差异，但顺序基本是：

打开应用 → 连接模型 → 选择工作区 → 新建任务 → 开始对话

如果你还没有模型服务，先看下一节。

2.2 连接模型

DSH 需要一个模型来“思考”。通常有两种方式：

  1. DeepSeek 官方账号/API：在设置里登录或填入 API Key；
  2. 兼容 OpenAI 接口的提供方：填入 Base URL、API Key、模型名。

操作路径

通常在：

设置（Settings） → 模型（Models） → 添加/选择提供方

你需要准备：

  • Provider（提供方）；
  • API Key；
  • 模型名称（例如 deepseek-chat / deepseek-flash，以实际提供方为准）；
  • 可选的 Base URL。

怎么判断成功

  • 设置页显示模型已连接；
  • 新建任务后，Agent 能正常回复；
  • 没有 401、Invalid API key 之类的错误。

常见错误：401

401 基本只有一个意思：Key 不对，或者没有生效。

检查：

  • Key 是否复制完整；
  • 是否有多余空格；
  • 提供方和 Base URL 是否匹配；
  • 账号是否有余额/权限；
  • 是否把别的服务的 Key 填到了这里。

不要把 API Key 贴进对话里让 Agent 帮你检查。 在设置页里改。

2.3 选择工作区

工作区就是 Agent 工作的文件夹。

第一次使用，建议这样做：

  1. 在桌面或文档目录新建一个空文件夹，例如 dsh-test；
  2. 在里面放一两个不重要的文本文件；
  3. 在 DSH 里选择这个文件夹作为工作区。

为什么不用整个用户目录？

  • Agent 能看到的东西太多，容易误操作；
  • 上下文会变复杂；
  • 出问题不好回滚。

工作区选好后，Agent 的“当前目录”通常就是这个文件夹。它读写相对路径时，默认以这里为基准。

2.4 选择标准模式

新建任务时，通常会让你选一个 Agent Preset（模式）。

第一次使用，选 标准模式（Standard）。

标准模式有完整的日常工具：读写文件、运行命令、搜索、子代理、计划、待办、交付文件。

不要一上来选 创造模式（Creator）。创造模式是给“扩展 DSH 本身”用的，会多出插件管理、运行时检查等能力，也会带来更高的权限风险。第 7 章会详细讲。

2.5 界面地图

你不需要记住每个按钮，但要知道四类信息在哪里：

区域 你会看到什么
对话区 你输入任务，Agent 回复、解释、提问
工具卡片 Agent 调用工具的过程，例如“读取文件”“运行命令”“写入文件”
审批/权限提示 某些操作需要你点“允许”或“拒绝”
侧边栏/设置 会话列表、工作区、模型、插件、技能、模式

最重要的习惯：

不要只看 Agent 的最后一段话，要看它中间做了什么。

工具卡片会告诉你它读了哪些文件、跑了什么命令、改了什么东西。

2.6 第一次对话：只读、可观察

第一次不要让它改文件。先做两个只读练习。

练习一：自我介绍

输入：

你好。请用三句话介绍你能做什么、不能做什么。
先不要读取或修改任何文件。

观察它是否：

  • 说明自己是 Agent；
  • 说明需要工作区/权限；
  • 没有擅自调用工具。

练习二：只读盘点

输入：

请只读当前工作区的文件，按类型分组列出来。
不要修改任何文件，也不要运行会改变文件的命令。
最后告诉我你用了哪些工具。

你会看到类似这样的工具卡片：

读取目录
读取文件

如果它想写文件，你可以拒绝，并提醒：

这一步只需要只读，请不要写入。

2.7 第一次对话的目标

不是“让它做一件大事”，而是让你熟悉三件事：

  1. 它会在哪里工作：工作区；
  2. 它怎么做事：工具调用；
  3. 你怎么控制它：审批、拒绝、补充要求。

换一种入口：Web / Headless

  • Web：通常用 dsh --profile web 启动，浏览器打开带 token 的地址。界面与 Desktop 类似，适合远程服务器。
  • Headless：用 dsh --profile headless "你的任务" 一次性执行，没有图形界面，适合脚本/自动化。
  • Desktop：由桌面应用管理 desktop profile，不建议手动改它的配置文件。

本书后续仍以 Desktop 为主。

常见坑

  • 没连模型就开始任务：只会得到错误或空回复。
  • 工作区选得太大：先小后大。
  • 一上来就选创造模式：日常任务用标准模式。
  • 把 Key 贴在聊天里：在设置里填。
  • 只看最后一段话：中间的工具调用才是它真正做的事。

小结

  • 启动顺序：打开应用 → 连模型 → 选工作区 → 选标准模式 → 开始对话。
  • 401 先查 Key。
  • 工作区要小、要可回滚。
  • 第一次对话以只读为主，观察工具卡片。
  • 标准模式是日常默认；创造模式是另一件事。

第 3 章　第一次任务：把需求说清楚

约 4 分钟 · 1,789 字 · 11 个小节

本章你会学会

  • 用“目标 + 输入 + 约束 + 验收”描述任务；
  • 让 Agent 先计划、再执行；
  • 检查工具调用和文件改动；
  • 给出有效反馈；
  • 用 present 交付最终文件。

3.1 好任务的四个要素

很多人觉得 Agent“不好用”，其实是因为任务说得太模糊。

一个好任务至少包含四件事：

要素 回答什么问题 例子
目标 最终要得到什么？ 一份 summary.md
输入 从哪里拿材料？ notes/ 下的三篇文章
约束 不能做什么？有什么规则？ 不改原文件；中文；保留链接
验收 怎么算完成？ 三个标题都在；每篇 3–5 句；能打开

反例

帮我整理一下笔记。

问题：

  • 哪些笔记？
  • 整理成什么？
  • 能不能改原文件？
  • 什么算整理好？

正例

请阅读 notes/ 下的三篇 Markdown 文章，合并成一份 notes/summary.md。
要求：
1. 保留每篇的标题和原文链接；
2. 每篇写 3–5 句摘要；
3. 不要修改原文件；
4. 先给我一个执行计划，我确认后再写。
完成后告诉我你读了哪些文件、写了哪个文件，并检查 summary.md 是否存在。

区别不是“更长”，而是信息完整。

3.2 先计划，再执行

对稍微复杂一点的任务，建议先让 Agent 进入“计划”状态。

你可以直接说：

先不要改文件。请给我一个 3–5 步的计划，说明你准备读什么、写什么、怎么验证。

观察它的计划是否：

  • 覆盖了所有输入；
  • 说明了输出位置；
  • 包含验证步骤；
  • 没有偷偷扩大范围。

如果计划不对，先改计划，不要让它直接开干。

3.3 看工具调用

Agent 执行时，会显示工具卡片。你要重点看：

工具 你要关注什么
读文件 读的是不是正确的文件
写文件 写到了哪里，是否覆盖了原文件
运行命令 命令是否会删除/重置/推送
搜索网页 来源是否可靠
子代理 它派出去做了什么

一个实用习惯：

看到“写入/删除/覆盖/重置/推送”这类词，先停一下。

3.4 迭代：给具体反馈

Agent 第一版不完美很正常。有效反馈要具体：

模糊反馈

不太好，重写。

具体反馈

第二段太长了，压缩到 3 句以内。
保留原来的三个小标题，不要合并。
把原文链接放到每段末尾，不要放在开头。

具体反馈 = 指出位置 + 指出问题 + 给出标准。

3.5 验收：不要只看“完成了”

Agent 说“完成了”，不等于真的完成。你要检查：

  • 文件是否存在；
  • 内容是否符合要求；
  • 原文件有没有被改；
  • 链接是否可点；
  • 有没有遗漏输入；
  • 有没有引入不存在的事实。

可以要求它给出证据：

请列出你实际读取的文件、写入的文件，以及你用来验证的检查项。
不要只告诉我“已完成”。

3.6 交付：present 是什么

当任务产出是一个文件时，Agent 可能会调用 present。

present 的准确含义是：

把已经存在的文件声明为本次任务的最终交付物，让界面生成文件卡片，用户可以预览或用默认应用打开。

它：

  • 不创建文件；
  • 不上传文件；
  • 不复制文件内容；
  • 只记录路径和说明；
  • 文件内容不会进入模型上下文。

如果 Agent 直接说“文件在 notes/summary.md”，也可以；present 只是让交付更直观。

3.7 一个完整的第一次任务

第一步：准备

在工作区建：

notes/
  a.md
  b.md
  c.md

第二步：发任务

请阅读 notes/ 下的三篇文章，合并成 notes/summary.md。
要求：
1. 保留标题和原文链接；
2. 每篇 3–5 句摘要；
3. 不改原文件；
4. 先给计划，我确认后再执行；
5. 完成后检查 summary.md 是否存在，并告诉我你读了哪些文件。

第三步：看计划

确认它没有漏文件、没有要改原文件。

第四步：批准执行

观察工具卡片：读了三个文件，写了一个新文件。

第五步：验收

打开 summary.md，检查标题、链接、摘要长度。

第六步：迭代

如果第二篇太短，直接说：

第二篇摘要加到 4 句，保留原有链接，其他不动。

常见坑

  • 任务太大：一次只做一件可验收的事。
  • 没有验收标准：Agent 不知道什么算好。
  • 不看工具调用：它可能改了不该改的文件。
  • 只说“重写”：给具体位置和标准。
  • 把“完成”当“正确”：要检查证据。

小结

  • 好任务 = 目标 + 输入 + 约束 + 验收。
  • 复杂任务先计划，再执行。
  • 看工具卡片，尤其是写、删、跑命令。
  • 反馈要具体；验收要看证据。
  • present 是交付声明，不是上传。

第一部分练习

  1. 用“目标 + 输入 + 约束 + 验收”重写一个你最近想让 AI 做的任务。
  2. 在一个测试文件夹里，让 Agent 只读列出文件，并说明用了哪些工具。
  3. 让它生成一个 summary.md，然后检查原文件是否被改动。
  4. 用一句具体反馈让它修改摘要，而不是说“重做”。

第 4 章　工作区、文件与权限

约 4 分钟 · 2,054 字 · 11 个小节

本章你会学会

  • 理解工作区为什么是“安全边界”；
  • 知道 Agent 能读什么、写什么；
  • 分清 workspace-write 和 danger-full-access；
  • 避免删除、覆盖、密钥泄漏这类真实事故；
  • 用 AGENTS.md 给项目立规矩。

4.1 Workspace 到底是什么

Workspace 是一个文件夹。

Agent 的“当前目录”通常就是它。你让它读 notes/a.md，它会在工作区里找 notes/a.md。

工作区有三个作用：

  1. 范围：Agent 默认只在这里工作；
  2. 上下文：这里的文件、目录结构、AGENTS.md 会影响它的判断；
  3. 权限：很多安全策略以工作区为边界。

所以，工作区不是“随便选一个文件夹”，而是你给 Agent 划定的工作范围。

建议

  • 一个项目一个工作区；
  • 不要让工作区包含整个用户目录；
  • 重要项目先 git init，有版本可回滚；
  • 测试任务用 dsh-test 这类临时目录。

4.2 Agent 能读什么、写什么

Agent 通过工具操作文件，常见的是：

工具 作用 风险
读文件 查看内容 低；但可能读到敏感信息
列目录/搜索 找文件 低
写文件 新建或覆盖 高；可能覆盖原文件
编辑文件 局部替换 中；可能改错位置
执行命令 运行任意程序 很高；可能删除/重置/上传

注意：“读”也可能有风险。如果工作区里有 .env、密钥、客户资料，Agent 读到后会进入上下文，甚至出现在回复里。

最小权限原则

  • 只给它完成当前任务需要的目录；
  • 不要把整个家目录、整个代码仓库根目录随便给它；
  • 处理敏感数据时，先脱敏或复制到隔离目录。

4.3 两种常见权限模式

DSH 中常见的文件策略：

workspace-write

  • 可以读写工作区内的文件；
  • 工作区外通常只读或需要审批；
  • 适合绝大多数日常任务。

danger-full-access

  • 可以访问更大范围；
  • 能执行更高风险的操作；
  • 适合你明确知道自己在做什么的场景，例如安装插件、系统级调试。

不要因为“省事”就长期开 full access。 权限越大，一次误操作的后果越大。

审批提示

当 Agent 要执行敏感操作时，界面可能会问：

允许这次操作吗？

你有三个选择：

  • 允许一次：只放行这一次；
  • 拒绝：不让它做；
  • 停止任务：直接中断。

看到“删除”“覆盖”“reset”“push”“上传”“安装”这些词，先读清楚再点。

4.4 破坏性操作：先备份，再确认

Agent 可能做的危险动作包括：

  • 删除文件/目录；
  • 覆盖已有文件；
  • git reset --hard；
  • git push --force；
  • 修改系统配置；
  • 安装/卸载软件；
  • 上传文件到外部服务。

三条规则

  1. 重要文件先备份；
  2. 能用 git 就用 git，提交后再让它改；
  3. 让它先说明影响范围，再批准。

可以这样说：

在执行删除/覆盖之前，先列出会被影响的文件，并告诉我怎么回滚。
没有我的确认，不要执行。

git 是你的后悔药

如果项目在 git 里：

git add -A
git commit -m "before agent changes"

Agent 改坏了，你可以：

git diff
git restore .

不要在没有版本控制的情况下，让 Agent 大范围改重要文件。

4.5 密钥、密码、截图

这是最容易出事的地方。

不要做

  • 不要把 API Key、密码、Token 贴进对话；
  • 不要把 .env 内容复制给 Agent；
  • 不要让它把含密钥的文件上传/发送；
  • 不要截含密钥的屏幕给它看。

应该做

  • 密钥放环境变量或密钥管理工具；
  • 需要配置时，让 Agent 改“变量名”，不要改“值”；
  • 给它看脱敏后的样例；
  • 发现它读到了密钥，立即停止，轮换密钥。

Agent 的上下文可能被记录、被回放、被展示。贴进去的秘密，就当作已经泄露。

4.6 AGENTS.md：给项目立规矩

AGENTS.md 是放在工作区里的“项目规则”。Agent 会读它，并尽量遵守。

一个简单的例子：

# 项目约定

- 所有回复用中文。
- 不要修改 `dist/` 和 `node_modules/`。
- 修改代码前先读相关文件。
- 提交前运行 `pnpm test`。
- 删除文件前必须先问我。
- 不要读取 `.env`。

它适合放：

  • 代码风格；
  • 目录规则；
  • 禁止事项；
  • 测试命令；
  • 交付格式；
  • 团队约定。

注意：AGENTS.md 是“指令”，不是“强制沙箱”。它降低误操作概率，但不能替代权限控制。

4.7 工作区卫生

  • 一个任务一个目录；
  • 输入、输出、临时文件分开；
  • 处理完删除临时文件；
  • 不要把测试数据和个人资料混在一起；
  • 大文件先确认是否需要读。

马上试试

  1. 建一个 dsh-test 工作区；
  2. 在里面放一个 AGENTS.md，写三条规则；
  3. 让 Agent 读一遍，并复述它会遵守什么；
  4. 故意让它改一个文件，观察审批提示；
  5. 拒绝一次，看看它是否能停下来。

常见坑

  • 工作区选太大：误操作范围变大。
  • 长期开 full access：风险累积。
  • 不备份就让它删/改：没有回滚。
  • 把 Key 贴进对话：直接泄露。
  • 以为 AGENTS.md 是沙箱：它只是指令。

小结

  • 工作区是范围、上下文和权限边界。
  • 读也有风险；密钥不要进对话。
  • workspace-write 是日常默认；danger-full-access 要克制。
  • 破坏性操作先备份、先确认。
  • AGENTS.md 用来立规矩，但不能替代权限控制。

第 5 章　会话、上下文与记忆

约 4 分钟 · 1,921 字 · 11 个小节

本章你会学会

  • 理解 Session 和 Context Window；
  • 知道 Agent 为什么会“忘事”；
  • 区分“会话内记忆”和“跨会话记忆”；
  • 用文件、AGENTS.md、Skill 做长期记忆；
  • 管理上下文，避免越聊越慢、越聊越贵。

5.1 Session 是什么

Session 是一次连续对话。

在同一个 Session 里：

  • 你说过的话、Agent 的回复、工具结果，会形成历史；
  • Agent 能引用前面的内容；
  • 但历史不是无限的。

新建 Session：

  • 通常不会自动继承上一个 Session 的完整聊天记录；
  • 它会重新读取工作区、AGENTS.md、可用 Skill 等；
  • 适合开始一个新任务。

你可以把 Session 理解成“一次会议”。会议结束，新的会议不会自动记得上一次的每句话，除非你留下会议纪要。

5.2 Context Window：Agent 的“工作内存”

模型一次能处理的文本量是有限的，这个上限叫 Context Window（上下文窗口）。

进入上下文的东西包括：

  • 系统提示词；
  • 工具定义；
  • Skill 内容；
  • 你的消息；
  • Agent 的历史回复；
  • 工具返回结果；
  • 读进来的文件内容。

上下文满了会怎样

  • 变慢；
  • 变贵；
  • 开始忘掉早期内容；
  • 可能触发压缩（compaction）或截断；
  • 严重时，它会“自信地”用错误信息继续。

常见信号

  • 它开始重复问已经说过的事；
  • 它引用了错误的文件名；
  • 它忘记了你前面定的规则；
  • 回复越来越长、越来越散。

5.3 DSH 不会自动记住一切

这是新手最大的误解。

DSH 有 Session 日志，但不等于跨会话的长期记忆。

  • 同一个 Session：它记得聊天历史；
  • 新建 Session：它通常不会自动记得上一个 Session 的每句话；
  • 它可能读取工作区文件、AGENTS.md、Skill；
  • 如果你装了记忆插件，才可能有额外的跨会话记忆。

所以，重要信息要落到文件里：

  • 项目背景 → PROJECT.md；
  • 约定 → AGENTS.md；
  • 进度 → TODO.md 或任务列表；
  • 决策 → DECISIONS.md；
  • 交付物 → 输出文件。

能被文件记住的，不要指望聊天记住。

5.4 新会话 vs 继续会话

场景 建议
开始一个全新任务 新建 Session
同一任务继续做 继续当前 Session
当前 Session 太长、开始混乱 让它先写总结，再新建
换了一个完全不同的项目 换工作区 + 新建 Session
只想问一个独立问题 新建 Session，避免污染上下文

长任务的做法

  1. 让 Agent 把当前进度写到 PROGRESS.md；
  2. 让它列出“已完成 / 未完成 / 下一步”；
  3. 新建 Session；
  4. 第一句话让它读 PROGRESS.md 和 AGENTS.md。

这比无限延长一个 Session 更稳。

5.5 用文件做“长期记忆”

一个简单可复用的结构：

project/
  AGENTS.md        # 规则
  PROJECT.md       # 项目背景
  DECISIONS.md     # 关键决策
  PROGRESS.md      # 进度
  TODO.md          # 待办
  notes/           # 资料
  output/          # 交付物

每次新 Session，先让它读：

请先读 AGENTS.md、PROJECT.md、PROGRESS.md，然后用三句话复述当前状态。
在复述之前不要改任何文件。

这样它不需要“记住”所有聊天，也能快速恢复上下文。

5.6 Context 卫生

  • 不要一次读入大量无关文件；
  • 让 Agent 先搜索、再读需要的部分；
  • 长文档分段读；
  • 工具输出很大时，要求摘要或只取关键段；
  • 任务完成后，把结论写进文件，而不是留在聊天里；
  • 不要在一个 Session 里混很多不相关任务。

一个实用提示词

请只读取与当前任务最相关的 3 个文件。
如果需要更多，先告诉我为什么。
不要一次性把整个目录读进来。

5.7 记忆插件与记忆文件

有些插件提供“跨会话记忆”：

  • 自动提取事实；
  • 存储到本地或云端；
  • 下次对话时召回。

它们有用，但不是魔法：

  • 可能召回错误；
  • 可能把旧信息当新信息；
  • 可能增加上下文和成本；
  • 需要隐私和权限评估。

对 0 基础用户，建议先用文件 + AGENTS.md 这种可控方式。等你有明确需求，再考虑记忆插件。

马上试试

  1. 让 Agent 写一个 PROJECT.md，记录当前任务目标和约束；
  2. 新建 Session；
  3. 第一句话让它读 PROJECT.md，复述目标；
  4. 观察它是否能在没有旧聊天记录的情况下继续工作。

常见坑

  • 以为新 Session 会记得旧 Session：不会自动记得。
  • 把所有资料一次性塞进上下文：又慢又贵。
  • 长 Session 里反复改需求：上下文污染。
  • 只让 Agent “记住”而不落文件：下次就没了。
  • 记忆插件当真相：召回可能错。

小结

  • Session 是一次对话；Context Window 是工作内存。
  • 上下文会满，满了会忘、会慢、会贵。
  • DSH 不自动跨 Session 记住一切。
  • 重要信息落文件；长任务先总结再换 Session。
  • 记忆插件是补充，不是替代。

第 6 章　工具与技能：Agent 的手和脑

约 4 分钟 · 2,086 字 · 12 个小节

本章你会学会

  • 认识 Agent 常用工具的分类；
  • 看懂工具调用卡片和审批；
  • 用计划、待办、子代理处理多步任务；
  • 理解 Skill 是什么，和 Tool / Plugin 的区别；
  • 正确使用 present；
  • 避免“工具用太多”和“技能装太多”。

6.1 工具的分类

你不需要记住每个工具名，只要知道它们大概分成几类。

你想做什么 工具类型 例子
看文件 读 读文件、列目录、搜索内容
改文件 写 新建、覆盖、局部编辑
跑程序 执行 终端命令、测试、构建
查资料 搜索 网页搜索、抓取网页
拆任务 协作 子代理、工作流
管理进度 计划 计划模式、待办清单、目标
交付 交付 present
问你 交互 提问、确认

一个原则

能只读，就先只读；能小步，就不要大步。

6.2 工具卡片与审批

每次工具调用，界面通常会显示：

  • 工具名；
  • 参数（例如文件路径、命令）；
  • 结果（成功/失败/输出）；
  • 有时会要求你批准。

你要重点看：

  • 路径对不对；
  • 命令有没有破坏性；
  • 输出有没有异常；
  • 它有没有跳过你的约束。

拒绝也是一种能力

如果它要做你没允许的事：

停。这一步不要执行。
先解释你为什么需要这个操作，以及有没有只读替代方案。

6.3 计划与待办

复杂任务建议先计划。

计划模式

让 Agent 先给出步骤，不执行：

先进入计划模式。给我一个 5 步以内的计划，说明每步要读/写什么、怎么验证。
我确认后再执行。

待办清单

执行阶段可以让它维护一个 todo：

请把任务拆成 todo，完成一项就更新一项。
不要一次开始所有项。

好处：

  • 你能看到进度；
  • 它不容易漏步骤；
  • 长任务更容易恢复。

6.4 子代理与工作流

子代理（subagent）

子代理是一个独立的 Agent，有自己的上下文。适合：

  • 独立的调研；
  • 并行的资料整理；
  • 让主 Agent 不被大量中间结果淹没。

你可以说：

派一个子代理去调研这三个链接，只返回要点和来源。
主任务继续做本地文件整理。

注意：

  • 子代理也要消耗模型调用；
  • 它的结果可能不准确；
  • 父 Agent 要负责验收。

工作流（workflow）

工作流是用脚本编排多个子代理，适合批量、并行、多阶段任务。

对 0 基础用户，先不用碰。等你熟悉子代理，再考虑。

6.5 Skill 是什么

Skill 是一份“操作手册”，通常是一个文件夹，里面有 SKILL.md。

它告诉 Agent：

  • 什么时候用这个技能；
  • 步骤是什么；
  • 有哪些坑；
  • 可以读哪些参考资料；
  • 可以运行哪些脚本。

Skill 和 Tool 的区别

Tool Skill
本质 可执行动作 知识与流程
例子 读文件、跑命令 “如何做一次代码审查”
谁执行 Harness Agent 阅读后按步骤做
上下文 schema 常驻 按需加载

Skill 和 Plugin 的区别

  • Skill 是知识，通常不直接提供新工具；
  • Plugin 是运行时扩展，可以提供新工具、服务、界面；
  • 有些 Plugin 会自带 Skill。

渐进披露

好的 Skill 不会一上来把几千行塞进上下文。它通常：

  1. 先只加载名称和描述；
  2. 任务匹配时，加载 SKILL.md；
  3. 需要细节时，再读 references/ 或运行脚本。

这就是为什么 Skill 可以很多，但不会瞬间撑爆上下文。

6.6 怎么用 Skill

通常有两种方式：

  1. 自动匹配：Agent 根据任务描述选择相关 Skill；
  2. 显式点名：你说“用 xxx 这个 Skill”。

如果你知道有合适的 Skill：

请使用 `code-review` 这个 Skill 来审查这次改动。
先读它的 SKILL.md，再按步骤执行。

如果你不确定：

当前有哪些 Skill 和我的任务相关？先列出来，不要直接执行。

装 Skill 的注意事项

  • 只装可信来源；
  • 看它有没有脚本、会访问什么；
  • 不要把密钥写进 Skill；
  • 装太多会占用元数据上下文；
  • 版本要跟 CLI/插件对齐。

6.7 present：交付文件

当任务产出是文件时，Agent 可能调用 present。

准确含义：

把已经存在的文件声明为最终交付物，让界面生成卡片，用户可以打开。

它不创建、不上传、不复制内容；只记录路径和说明。

你可以要求：

完成后用 present 交付最终文件，最多 2 个，不要把所有中间文件都 present。

6.8 工具使用的常见误区

  • 工具越多越好：不，工具多会增加选择和上下文成本。
  • 让 Agent 一次读整个目录：先搜索，再读相关文件。
  • 子代理当免费劳动力：也要花 token，也可能错。
  • Skill 装一堆：只装当前需要的。
  • 不看工具结果：只看总结容易漏错。

马上试试

  1. 让 Agent 为一个任务写 3 步计划；
  2. 让它用 todo 跟踪执行；
  3. 让它只读搜索相关资料，不直接读整个目录；
  4. 让它用 present 交付一个最终文件；
  5. 问它：“你刚才用了哪些工具？哪些是只读的？”

小结

  • 工具分读、写、跑、搜、协作、计划、交付。
  • 先只读、再小步执行；看工具卡片。
  • 子代理/工作流适合拆任务，但不是免费。
  • Skill 是知识，Tool 是动作，Plugin 是运行时扩展。
  • present 是交付声明，不是上传。

第二部分练习

  1. 给你的测试工作区写一个 AGENTS.md，包含三条禁止事项。

第 7 章　模式与 Preset：同一个模型，不同工作方式

约 4 分钟 · 2,167 字 · 12 个小节

本章你会学会

  • 理解 Preset 不是模型，也不是另一个软件；
  • 分清标准、创造、PTC、极简四种常见模式；
  • 知道什么任务该用哪种模式；
  • 理解“自定义 Preset”的正确做法；
  • 避免把“模式”当成“安全隔离”。

7.1 一个比喻：Preset 是“角色卡”

同一个模型，可以有不同的工作方式：

  • 日常写代码、整理文件；
  • 专门扩展 DSH 本身；
  • 批量调用工具、做数据分析；
  • 只保留最少工具，快速回答问题。

这些“工作方式”就是 Preset（预设）。

你可以把 Preset 理解成一张“角色卡”或“装备方案”：

同一个 Agent 引擎
  + 不同的工具
  + 不同的提示词
  + 不同的 Skill
  + 不同的策略
= 不同的工作模式

它不换模型，不换运行时，不换沙箱；它只换“这个 Agent 这次拿到哪些能力”。

7.2 标准模式（Standard）

这是日常默认模式。

适合：

  • 写代码；
  • 读写文件；
  • 搜索资料；
  • 整理文档；
  • 做表格；
  • 日常问答；
  • 一般的多步任务。

它通常包含：

  • 文件读写；
  • 终端命令；
  • 网页搜索/抓取；
  • 子代理；
  • 计划、待办、目标；
  • 交付文件；
  • 技能系统。

如果你不知道选什么，选标准模式。

7.3 创造模式（Creator）

创造模式不是“更聪明的标准模式”。它是用来扩展 DSH 本身的模式。

它通常会多出：

  • 运行时检查：查看 DSH 内部的 Service、Config、Tool、Skill、界面 Slot；
  • 插件管理：安装、启用、停用、卸载插件；
  • 开发指引：Cordis 插件、Bundle、Preset 的写法和模板。

适合：

  • 写一个 DSH 插件；
  • 给 DSH 加一个工具/界面；
  • 做一个自定义 Preset；
  • 调试插件为什么没加载。

不适合：

  • 日常写代码；
  • 普通文件整理；
  • 你不需要扩展 DSH 的时候。

为什么？因为它多出的工具和权限会占用上下文，也带来更高的操作风险。日常任务用标准模式更轻、更安全。

7.4 PTC 模式

PTC 是 Programmatic Tool Calling 的缩写，可以理解为“用写代码的方式组织工具调用”。

它适合：

  • 批量调用工具；
  • 对结果做筛选、去重、统计、汇总；
  • 需要循环、条件、组合的任务；
  • 数据分析类任务。

它不一定更快，也不一定更省 token；取决于任务和实现。日常任务用标准模式即可。

7.5 极简模式（Minimal）

极简模式只保留很少的工具，通常用于：

  • 快速问答；
  • 小规模读写；
  • 想尽量减少上下文和工具干扰的场景。

它的能力边界更窄。需要复杂操作时，换回标准模式。

7.6 四种模式怎么选

你的任务 建议
日常写代码、整理文件 标准模式
做 DSH 插件、改 Preset 创造模式
批量工具调用、数据分析 PTC
快速问答、小任务 极简模式
不确定 标准模式

7.7 Preset 到底是什么

在 DSH 里，Preset 是一份 Agent 的子插件列表，加上名称、描述、排序等元数据。

它通常长这样：

id: standard
name: 标准模式
order: 1
plugins:
  - persona
  - tool-bash
  - tool-fs
  - tool-web
  - ...

几个关键点：

  • 它由 @deepseek-ai/dsh-agent-preset 这个插件声明；
  • 由 agent-preset-registry 管理；
  • 每个 Session 选择一个 Preset；
  • 定义会提前加载，但编辑只影响新创建的 Agent；
  • 运行中的 Agent 保留它启动时的版本；
  • 子 Agent 通常继承父 Agent 的 Preset。

它不是

  • 不是模型；
  • 不是沙箱；
  • 不是另一个进程；
  • 不是“更高级的模型”。

它也不是安全隔离

Preset 可以隔离工具和服务，但它不是安全沙箱。

  • 插件代码仍然在 Host 进程执行；
  • 文件权限、审批、沙箱是另一套机制；
  • 不要因为“切了模式”就认为风险消失。

7.8 自定义 Preset

你可以创建自己的模式，例如：

  • “代码审查模式”：只读，先报告问题，不直接改文件；
  • “写作模式”：固定文风、固定输出结构；
  • “数据分析模式”：只允许读数据和跑分析脚本。

正确做法通常是：

  1. 在创造模式里描述你要的模式；
  2. 让 Agent 生成一个 Bundle 补丁；
  3. 通过 Plugin Manager 安装；
  4. 在新建任务时选择它。

不建议：

  • 手动去改 ~/.dsh/.agent-presets/ 旧目录；
  • 直接编辑 profile 的 package.json；
  • 复制一个内置 Preset 后长期不合并更新。

自定义 Preset 的“整份替换”特性意味着：你覆盖后，内置 Preset 后续新增的工具不会自动出现。要定期检查。

7.9 常见误区

  • “创造模式更聪明”：不是。它只是多了扩展 DSH 的工具和知识。
  • “换 Preset 就换了模型”：不是。模型由模型设置决定。
  • “Preset 是安全隔离”：不是。安全靠权限/沙箱/审批。
  • “Preset 越多越好”：不是。多一个模式就多一份维护成本。
  • “自定义 Preset 会自动跟进内置更新”：不会，覆盖是整份替换。

马上试试

  1. 新建任务，选择标准模式；
  2. 问 Agent：“你现在有哪些工具？哪些是只读的？”
  3. 再新建一个任务，选择创造模式；
  4. 问同样的问题，对比多了什么；
  5. 不要执行任何安装/修改，先观察差异。

小结

  • Preset 是 Agent 的能力组合，不是模型/沙箱。
  • 标准模式是日常默认；创造模式用于扩展 DSH；PTC 适合批量工具调用；极简模式适合小任务。
  • 运行中的 Agent 保留启动时的 Preset 版本。
  • 自定义 Preset 要走 Bundle + Plugin Manager，不要手改旧目录。
  • Preset 不等于安全隔离。

第 8 章　插件、Bundle 与 Profile：给 DSH 装能力

约 5 分钟 · 2,482 字 · 12 个小节

本章你会学会

  • 分清 Plugin、Bundle、Profile 三个词；
  • 知道一个插件是怎么被“装进去”的；
  • 用 Plugin Manager 安装、启用、停用、卸载；
  • 理解第三方插件的信任边界；
  • 遇到“装了但不生效”时怎么排查。

8.1 三个词，三个层级

先记住一句话：

Plugin 是能力，Bundle 是安装包，Profile 是工作环境。

词 你可以理解成 回答的问题
Plugin 一个可插拔的能力模块 运行的时候执行什么？
Bundle 一个可安装的“补丁包” 哪些配置和代码一起分发？
Profile 一套安装环境 这个环境装了哪些 Bundle？

Plugin

Plugin 是运行时单元。它可以：

  • 注册工具；
  • 注册服务；
  • 注册 Skill；
  • 添加界面；
  • 监听事件；
  • 改变 Agent 的行为。

例如，一个笔记类插件可以注册一组笔记工具、一个 Config 和一个 Skill。

Bundle

Bundle 是一个 npm 包，里面通常有：

  • 一个 cordis.patch.yml（或一组 patch 文件）；
  • 要挂载的插件代码；
  • 可能还有 Skill、界面资源、图标。

它的作用是：

  • 把“要加哪些插件、怎么配置”打包；
  • 让用户一条命令安装；
  • 安装后，它的配置行仍然可以被上层覆盖。

一个 Bundle 可以挂载多个 Plugin；一个 Plugin 也可以被不同的 Bundle 引用。

Profile

Profile 是安装环境，通常对应：

  • desktop：桌面应用；
  • web：浏览器；
  • headless：命令行一次性执行。

它里面有：

  • 已安装的 Bundle 列表；
  • 自己的 cordis.patch.yml；
  • 第三方插件依赖。

Profile 决定“这个环境装了什么”，Bundle 决定“装的东西包含什么”，Plugin 决定“实际运行什么”。

8.2 它们和 Preset 的关系

Profile（desktop）
 ├─ Bundle A（dsh-base）
 ├─ Bundle B（dsh-web-app）
 │    └─ 声明 Preset: standard / creator / ...
 └─ Bundle C（你的插件）
      └─ 挂载 Plugin: 你的工具

Preset（standard / creator）
 └─ 给某个 Agent 选择一组 Plugin
  • Bundle 可以声明 Preset；
  • Preset 是“给哪个 Agent 用哪些 Plugin”；
  • Profile 是“这个环境装了哪些 Bundle”；
  • Plugin 是“真正执行的能力”。

8.3 用 Plugin Manager 安装

在 Desktop 里，通常有 Plugin Manager / 插件页面。

基本流程：

  1. 打开插件页面；
  2. 搜索或选择要安装的 Bundle；
  3. 阅读说明、权限、依赖；
  4. 确认安装；
  5. 按提示重启/重载；
  6. 检查工具、Skill、界面是否出现。

安装前要看的

  • 作者/来源是否可信；
  • 它要求什么权限；
  • 是否依赖外部 CLI/服务；
  • 是否会执行安装脚本；
  • 是否和已有插件重名/冲突；
  • 有没有卸载方式。

安装后要检查

  • 插件是否显示“已启用”；
  • 工具列表里有没有新工具；
  • Skill 列表里有没有新 Skill；
  • 有没有报错/警告；
  • 是否需要重启。

8.4 为什么“装了但不生效”

常见原因：

现象 可能原因
插件列表里有，但工具没有 没启用；需要重启/重载；依赖缺失
启动报错 版本不兼容；缺 peer 依赖；配置错误
工具名冲突 和另一个插件用了同一个名字
需要登录/CLI 外部依赖没装/没登录
只在某个模式里有 工具被挂在某个 Preset 里，不是全局
改了代码不生效 服务端插件需要重载；不是热更新

排查顺序

  1. 看 Plugin Manager 的状态和错误；
  2. 看是否需要重启；
  3. 看依赖/版本；
  4. 看是否和已有插件冲突；
  5. 看工具是否只在某个 Preset 中；
  6. 看日志/诊断。

8.5 配置插件

很多插件有配置项，例如：

  • 可执行文件路径；
  • API 地址；
  • 超时；
  • 输出上限。

在 DSH 里，插件通常用 Config schema 声明这些字段，Plugin Manager 会显示成表单。

原则：

  • 优先用界面配置；
  • 不要手动改 profile 的 package.json；
  • 不要手动改 cordis.patch.yml，除非你知道层顺序；
  • 改完要重载/重启；
  • 配置里的密钥要放在安全位置。

8.6 第三方插件的信任边界

这是最重要的一节。

插件不是“配置文件”，它可能执行代码。

安装第三方插件，相当于让别人的代码在你的 DSH 进程里运行。它可能：

  • 读取你的文件；
  • 调用网络；
  • 执行命令；
  • 修改配置；
  • 安装依赖；
  • 运行安装脚本。

所以：

  • 只装可信来源；
  • 看权限和代码；
  • 不要给不必要的 full access；
  • 先在测试工作区试；
  • 出问题能卸载/回滚；
  • 不要把密钥交给不信任的插件。

8.7 卸载与回滚

安装前就要想好怎么卸载：

  • Plugin Manager 里能否停用/移除；
  • 是否会留下配置/数据；
  • 是否会改 profile 的 bundle 列表；
  • 是否需要重启；
  • 有没有版本回退。

重要环境先备份 profile，或至少记录安装前的状态。

马上试试

  1. 打开 Plugin Manager，看看当前装了哪些 Bundle；
  2. 找到“已启用/已停用”的区别；
  3. 不要急着安装新插件，先读一个插件的说明和权限；
  4. 找一个你已经在用的插件，看看它注册了哪些工具/Skill；
  5. 写下：如果它出问题，你怎么停用它？

常见坑

  • 把 Plugin 和 Bundle 混为一谈：一个是能力，一个是安装包。
  • 以为装了 Bundle 就一定启用：还要看选择/重载/依赖。
  • 手动改 profile 配置：容易破坏层顺序。
  • 不看权限就装：插件可以执行代码。
  • 装完不重启：很多插件需要重载才生效。

小结

  • Plugin = 能力，Bundle = 安装包，Profile = 工作环境。
  • Preset 决定“给哪个 Agent 用哪些 Plugin”。
  • 用 Plugin Manager 安装/启用/卸载；不要手改 profile。
  • 第三方插件是代码，不是纯配置；信任和权限第一。
  • 装了不生效，先查状态、重载、依赖、冲突、Preset 范围。

第三部分练习

  1. 用一句话向你朋友解释 Plugin、Bundle、Profile 的区别。
  2. 打开 Plugin Manager，记录当前启用的 Bundle 数量。
  3. 找一个插件，阅读它的权限/依赖，判断你是否愿意安装。
  4. 解释为什么“Preset 不是安全沙箱”。
  5. 写下一个“插件装坏了怎么回滚”的步骤清单。

第 9 章　创造模式：从使用者到扩展者

约 4 分钟 · 1,993 字 · 10 个小节

本章你会学会

  • 创造模式到底是什么，不是什么；
  • 它比标准模式多了哪些能力；
  • 什么时候该用，什么时候不该用；
  • 一次完整的“做插件”流程；
  • 不会编程的人怎么参与；
  • 怎么避免把 DSH 改坏。

9.1 创造模式是什么

创造模式是 DSH 的一个 Agent Preset，内部 id 是 cordis。

它不是：

  • 另一个模型；
  • 另一套运行时；
  • 另一个软件；
  • 更聪明的标准模式。

它是：

在标准任务工具之上，额外提供运行时检查、插件管理、以及插件/Preset 开发指引的一种工作模式。

它和标准模式共用：

  • 同一个 Agent loop；
  • 同一个模型；
  • 同一个沙箱/权限系统；
  • 绝大部分任务工具。

差别只在“composition（插件组合）”。

9.2 它比标准模式多了什么

通常包括三类能力。

1. 运行时检查

可以查询 DSH 当前真实的：

  • Service 方法；
  • Config schema；
  • Tool schema；
  • Skill 列表；
  • 界面 Slot / theme token。

这解决了一个大问题：不用猜 API。

2. 插件管理

可以：

  • 列出已安装的 Bundle；
  • 安装/启用/停用/卸载；
  • 修改 profile 的插件选择；
  • 查看安装结果和警告。

这些操作会持久化到 profile，影响所有 Session，并在重启后保留。

3. 开发指引

创造模式会挂载一组 authoring Skill，告诉你：

  • 怎么写 Cordis 插件；
  • 怎么写 Bundle patch；
  • 怎么创建/覆盖 Preset；
  • 怎么验证插件真的生效。

它还会提供模板和参考资料，按需加载。

9.3 什么时候该用

适合：

  • 想给 DSH 加一个工具；
  • 想加一个界面/按钮/面板；
  • 想做一个自定义模式；
  • 想调试“插件为什么没加载”；
  • 想把自己的工作流封装成插件。

不适合：

  • 日常写代码；
  • 普通文件整理；
  • 只是想让 Agent 帮你查资料；
  • 你不需要扩展 DSH 的时候。

原因：

  • 多出的工具和 Skill 会占用上下文；
  • 插件安装是高风险操作；
  • 日常任务用标准模式更轻。

9.4 安全边界：这是高信任模式

创造模式可以做很多“普通模式不能做”的事，因为：

  • 安装插件会在 Host 进程执行代码；
  • 修改 profile 会影响所有 Session；
  • 插件可能读写文件、访问网络、运行命令；
  • 这些代码在 workspace sandbox 之外执行。

所以：

  • 插件管理通常需要 full access 或逐次审批；
  • 不要给不信任的代码 full access；
  • 先在测试 profile/工作区试；
  • 重要配置先备份；
  • 出问题要能停用/回滚。

创造模式不是“安全模式”，它是“高信任的扩展模式”。

9.5 一次完整的“做插件”流程

下面是一个通用流程，不要求你会写代码，但要求你能描述目标和验收。

第 1 步：描述能力

不要一上来就说“帮我写个插件”。先说清楚：

我想给 DSH 加一个能力：
- 它做什么；
- 在哪里使用（聊天/按钮/面板/工具）；
- 输入是什么；
- 输出是什么；
- 怎么验证它成功；
- 不需要做什么。

第 2 步：让它先检查

先不要写代码。
请用运行时检查工具，确认：
1. 这个能力应该挂在哪一层（Host 插件 / Preset 插件 / 纯配置）；
2. 可用的 Service / Slot / Tool API；
3. 是否需要新的 Bundle；
4. 有没有现成模板。
把结论和风险列给我。

第 3 步：做最小版本

先做一个最小可用版本。
不要做额外功能、不要做多个变体。
给出文件清单、安装方式、验证步骤。

第 4 步：安装并验证

安装到当前 profile。
安装后告诉我：
- 安装结果（applied / warnings）；
- 新增了哪些工具/Skill/界面；
- 怎么验证；
- 怎么卸载。

第 5 步：修复与迭代

只修观察到的问题，不要无限加功能。

第 6 步：收尾

请给出：
- 插件位置；
- 安装/卸载方式；
- 已验证的内容；
- 未验证的内容；
- 已知限制。

9.6 不会编程的人怎么参与

你不需要自己写代码，但你需要做三件事：

  1. 说清楚目标：用户是谁、在什么场景、输入输出是什么；
  2. 审查结果：它有没有做你没要求的事？有没有权限过大？
  3. 验收：按你定义的场景试一遍，不通过就具体反馈。

你可以要求：

不要只告诉我“完成了”。
请给出：
- 改了哪些文件；
- 新增了哪些能力；
- 我怎么手动验证；
- 如果失败，怎么回滚。

9.7 常见误区

  • “创造模式是高级版标准模式”：不是。它是扩展模式。
  • “装插件只是改配置”：不是。插件可能执行代码。
  • “装了就会自动生效”：不一定，可能需要重载/重启。
  • “Preset 可以当沙箱”：不可以。
  • “让 Agent 直接改 profile 文件”：不要，用 Plugin Manager。
  • “一次做很大”：先最小版本，再迭代。

马上试试

  1. 新建一个创造模式任务；
  2. 不要安装任何东西；
  3. 让它列出当前可用的运行时检查能力；
  4. 问它：“如果我要加一个只读工具，应该挂在哪一层？为什么？”
  5. 读它的回答，不执行。

小结

  • 创造模式是 cordis Preset，不是模型/运行时。
  • 它多出运行时检查、插件管理、开发指引。
  • 适合扩展 DSH，不适合日常任务。
  • 插件代码在 Host 执行，必须有信任和回滚方案。
  • 先最小版本，再验证、再迭代。

本章你会学会

10.2 怎么读诊断信息

先看界面

  • 红色错误；
  • 工具卡片的失败原因；
  • Plugin Manager 的 warnings；
  • 模型设置的状态。

再看上下文

  • 当前工作区对不对；
  • 当前模式对不对；
  • 当前插件是否启用；
  • 当前 Session 是否太长。

最后看日志

Desktop/CLI 通常会有日志或诊断入口。CLI 用户可以：

dsh --profile web --dump-config

查看实际组合的配置。不要在不理解的情况下直接改 profile 文件。

一个通用排查顺序

1. 最小复现
2. 换新 Session
3. 换标准模式
4. 停用最近装的插件
5. 检查模型/网络
6. 检查工作区/权限
7. 看日志/诊断
8. 再考虑重装/回滚

10.3 安全清单

每次开始重要任务前，问自己：

[ ] 工作区是不是只包含需要的文件？
[ ] 重要文件有没有备份/git 提交？
[ ] 是否只需要只读？能不能先只读？
[ ] 是否要执行删除/覆盖/推送/上传？
[ ] 是否要把密钥/密码/隐私数据给它看？
[ ] 插件来源是否可信？
[ ] 是否真的需要 full access？
[ ] 出问题怎么回滚？

三条底线

  1. 密钥不进对话；
  2. 破坏性操作先备份、先确认；
  3. 不信任的插件不给高权限。

10.4 成本与用量

Agent 的成本主要来自 token：

  • 上下文越长，越贵；
  • 读大文件、长网页，会显著增加；
  • 子代理/工作流会额外调用模型；
  • 频繁重试也会增加。

省钱习惯

  • 只读需要的文件；
  • 长文档分段；
  • 任务完成就总结成文件，换新 Session；
  • 不用子代理时不要开；
  • 选合适的模型，不要所有任务都用最贵的。

10.5 继续学习路线

第 1 周：日常使用

  • 用标准模式完成 3 个真实任务；
  • 练习“目标 + 输入 + 约束 + 验收”；
  • 学会看工具卡片和审批。

第 2 周：工作区与上下文

  • 给项目写 AGENTS.md；
  • 用 PROJECT.md / PROGRESS.md 管理长任务；
  • 练习新 Session 恢复。

第 3 周：工具与技能

  • 用 todo 管理多步任务；
  • 试一个子代理；
  • 读一个 Skill 的 SKILL.md；
  • 用 present 交付文件。

第 4 周：扩展

  • 读第 8 章，理解 Plugin/Bundle/Profile；
  • 在创造模式里做一个小工具；
  • 学会安装、验证、卸载；
  • 写一份自己的插件说明。

10.6 一页纸速查

Agent = Model + Harness

日常任务 → 标准模式
扩展 DSH → 创造模式
批量工具 → PTC
小任务   → 极简模式

工作区 = 文件夹 + 权限边界
Session = 一次对话
Context = 工作内存，会满
Skill   = 知识/流程
Tool    = 动作
Plugin  = 运行时能力
Bundle  = 安装包
Profile = 安装环境
Preset  = 单 Agent 的能力组合

好任务 = 目标 + 输入 + 约束 + 验收
先只读，再写入
先计划，再执行
破坏性操作先备份
密钥不进对话

小结

  • 排错从“最小复现 + 新 Session + 标准模式 + 停用新插件”开始。
  • 安全三条底线：密钥、备份、权限。
  • 成本主要来自上下文和模型调用。
  • 学习路线：日常 → 工作区 → 工具/技能 → 插件。
  • 先会用，再扩展；不要一上来做很大的插件。

B. 10 个提示词模板

1. 只读盘点

请只读当前工作区，列出文件并按类型分组。
不要修改任何文件，也不要运行会改变文件的命令。
最后说明你用了哪些工具。

2. 先计划

先不要执行。请给我一个 3–5 步计划：
每步做什么、读/写哪些文件、怎么验证。
我确认后你再开始。

3. 生成文档

请阅读 [文件列表]，生成 [输出文件]。
要求：[结构/长度/语言/链接]。
不要修改原文件。
完成后检查输出文件是否存在，并列出你读过的文件。

4. 代码审查

请审查这次改动，优先找 bug、边界情况、测试缺口。
按严重程度排序，指出文件和行号。
先不要改代码，只给报告。

5. 调试

请先复现问题，再提出最多 3 个假设。
每次只验证一个假设，并给出证据。
不要在没有验证的情况下大改代码。

6. 资料调研

请调研 [主题]，优先使用一手来源。
输出：结论、证据链接、反方观点、仍不确定的地方。
不要编造来源。

7. 数据整理

请读取 [输入]，按 [字段] 整理成 [输出格式]。
不要修改原始数据。
先给我字段映射和清洗规则，确认后再执行。

8. 写作

请按 [读者/语气/长度/结构] 写一篇 [主题]。
不要使用空泛套话；每个观点要有依据。
先给提纲，确认后再写全文。

9. 文件整理

请先只读列出 [目录] 的文件，给出整理方案。
不要删除/移动任何文件，等我确认。
方案要说明每个文件去哪、为什么。

10. 插件需求

我想给 DSH 加一个能力：[描述]。
先不要写代码。请检查：
1. 应该挂在哪一层；
2. 需要哪些 API/模板；
3. 最小版本是什么；
4. 怎么验证、怎么卸载。

C. 开始任务前的检查清单

[ ] 目标一句话说清楚了吗？
[ ] 输入文件/目录明确了吗？
[ ] 输出位置和格式明确了吗？
[ ] 有哪些禁止事项？
[ ] 怎么验收？
[ ] 需要备份/提交吗？
[ ] 是否需要只读先行？
[ ] 是否涉及密钥/隐私？
[ ] 是否需要安装插件/开高权限？

D. 任务完成检查清单

[ ] 输出文件真的存在吗？
[ ] 内容符合要求吗？
[ ] 原文件有没有被改？
[ ] 有没有遗漏输入？
[ ] 有没有编造事实/来源？
[ ] 有没有测试/验证证据？
[ ] 需要交付的文件 present 了吗？
[ ] 临时文件清理了吗？
[ ] 需要回滚时知道怎么做吗？

结语

DSH 不难用，难的是在它变强之前，先学会控制它。

记住三句话：

  1. 先只读，再写入。
  2. 先小步，再扩大。
  3. 密钥不进对话，破坏性操作先备份。

当你熟悉了这些，再去碰 Preset、Plugin、Bundle、Creator。那时你看到的不再是一堆名词，而是一套可以按需组合的工作台。
